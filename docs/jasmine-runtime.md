# Jasmine Runtime

`AssistantEvent` содержит тип события, владельца, время, Telegram provenance, текст или подпись, фото, ссылки на наблюдения и контекст ответа. Сейчас подключены сообщения и фото Telegram. `reminder_due`, `scheduled_event` и `external_event` представлены типами, но их источников пока нет.

## Один ход

```text
AssistantEvent
  -> базовый контекст: профиль и до 50 предыдущих сообщений
  -> JasminePlanner (LLM_MAIN для текста)
  -> общий реестр инструментов и политика runtime
  -> результат инструмента или наблюдение об ошибке
  -> следующий шаг планировщика или финальный черновик
  -> LLM_REPLY и Telegram outbox
```

**A skill is not a router destination.** Один ход может вызвать ноль инструментов, один инструмент или инструменты нескольких skills:

```text
one turn -> planner -> Skill A tool -> observation A
                    -> Skill B tool -> observation B -> response
```

`JasmineSkill` регистрирует инструменты и ленивый провайдер контекста. Инструмент объявляет имя, владельца, описание, JSON schema, риск (`read`, `low_write`, `confirm`), подтверждение и область идемпотентности. Runtime ограничивает ход пятью вызовами, проверяет аргументы и владельца, отклоняет неизвестные инструменты, повтор вызова и неподтвержденное действие. Ошибка исполнителя становится наблюдением. Факт успешной записи исходит только из доменного результата.

Структурированный `JasmineTrace` записывает корреляцию, шаг, инструмент, skill, итог и задержку в backend логах. Внутренние рассуждения модели не сохраняются.

## Coach

Coach теперь полный зарегистрированный skill. Его инструменты чтения: `get_active_session`, `get_current_workout_state`, `get_exercise_history`, `get_progression`, `fitness_question`.

Инструменты действий: `propose_workout`, `start_workout`, `log_set`, `correct_performance`, `replace_exercise`, `skip_exercise`, `add_exercise`, `replan_active_workout`, `finish_workout`, `abandon_workout`, `save_memory`, `save_transient_state`, `log_exercise` для полного отчета о тренировке, `continue_workout_clarification` для выбора упражнения или уточнения коррекции и `log_machine_metrics` для уже разобранного фото экрана тренажера.

Каждый инструмент вызывает существующий доменный код: `CoachAgent.executePlannedCalls`, `SessionService`, `LiveService`, генерацию предложений, workout ingestion или image machine workflow. Контекст активной сессии, выполненных подходов, истории и ответа на сообщение загружается по вызову Coach инструмента. Модель передает пользовательские формулировки и числа; приложение разрешает канонические session/workout/exercise ID. `CoachActionFact` возвращает подтвержденные идентификаторы, подход, нагрузку, статус, ссылки на записи и ID ревизии, когда он есть. Сочетание «сохрани состояние/предпочтение + предложи тренировку» сводится к одному `propose_workout`: прежний исполнитель записывает все вместе.

Coach write tools терминальные в текущем Telegram контракте: существующий исполнитель сохраняет доменное действие, provenance, outbox и статус update в одной транзакции. После такого инструмента runtime завершает ход; `LLM_REPLY` формулирует уже подтвержденный результат из outbox. Это сохраняет атомарность и исключает вторую запись или второй outbox для того же update.

## Оставшаяся переходная граница

**Общего `legacy.handle_message` больше нет.** Обычное текстовое действие тренировки не может попасть в старый message-level `Orchestrator.ProcessMessage` через Jasmine. Если LLM_MAIN недоступен, детерминированный планировщик выбирает конкретный `coach.*` инструмент. Большие текстовые отчеты о тренировке проходят через `coach.log_exercise` и прежний `IngestionPipeline`.

`legacy.handle_photo` пока выполняет специализированную обработку входящего изображения. `legacy.handle_specialized_text` допускает только JSON профиля, дневник питания и его исправления, продолжения разбора этикетки/изображения. Он вызывает соответствующие специализированные методы напрямую и отклоняет обычный текст тренировки. Прямой метод `Orchestrator.ProcessMessage` остается для старых callers/tests, но не является инструментом Jasmine и не используется для нормального Coach хода.

Следующий checkpoint: выделить оставшиеся профиль, питание и image workflow в собственные узкие инструменты с теми же транзакциями и убрать `legacy.handle_specialized_text`. Новые продуктовые возможности здесь не добавлялись.

## Telegram alpha response boundary

Финальную формулировку любого обычного ответа делает только `LLM_REPLY` в delivery worker. Доменные транзакции сохраняют изменения и `ReplyContext` в outbox; раннего вызова модели ответа в Coach и image analyzer больше нет. Delivery worker читает до 50 предыдущих сообщений, отдельно передает текущее входящее и сохраняет фактически отправленный текст. Ошибка или пустой ответ модели оставляет доставку в `failed` для повтора без повторной доменной записи. Активные промпты и ключи находятся в `internal/module/prompts/catalog.go`; их DB overrides хранятся в существующей `system_prompts`.
